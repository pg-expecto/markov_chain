## 1. Введение

Настоящее руководство содержит подробное описание всех аналитических отчётов, доступных в системе цепи Маркова, а также процедуры эмпирической оптимизации параметров адаптивного забывания и её интеграции с планировщиком задач `cron`. Материал предназначен для администраторов и аналитиков, обеспечивающих эксплуатацию модели прогнозирования рисков.

---

## 2. Аналитические отчёты цепи Маркова

Ниже представлены детальные пояснения для каждого из тринадцати отчётов, доступных в системе. Для каждого отчёта указаны его цель, структура вывода, ключевые метрики, их интерпретация и практические рекомендации по использованию.

---

### 2.1. `generate_full_analytical_report`

**Назначение**  
Формирует **сводный аналитический отчёт** в формате Markdown (массив строк), объединяющий все основные аспекты работы цепи Маркова за заданный период. Это «дашборд» для комплексной оценки модели.

**Параметры**  
- `p_start` (DATE, по умолч. 7 дней назад) – начало периода.  
- `p_end`   (DATE, по умолч. вчера) – конец периода.

**Что включает отчёт**  
1. Общий обзор состояния цепи (`mchain_summary_report`).  
2. Качество прогнозов (`mchain_quality_report`).  
3. Матрица переходов между макрогруппами (`mchain_state_transition_matrix_report`).  
4. Стабильность вероятностей по 7-дневным периодам (`report_stability_trend`).  
5. Скользящее качество прогнозов по дням (`report_quality_sliding`).  
6. Распределение состояний (топ-20 по частоте) (`state_distribution`).  
7. Эффективность забывания (результаты оптимизации) (`report_forgetting_effectiveness`).  
8. Калибровочная кривая за последний день периода (`report_daily_calibration`).

**Интерпретация**  
Отчёт предназначен для периодического (например, еженедельного) анализа состояния модели. Он позволяет:  
- Оценить, насколько модель достоверна и стабильна.  
- Выявить ухудшение качества прогнозов или рост нестабильности.  
- Понять, какие состояния наиболее часты и критичны.  
- Оценить эффективность текущих параметров забывания.  

**Рекомендации**  
- Регулярно генерируйте отчёт (например, по воскресеньям) и сохраняйте в систему мониторинга.  
- Обращайте внимание на разделы с пометками ⚠️ или 🔴 – они указывают на проблемы, требующие вмешательства.  
- Используйте отчёт для принятия решений о перенастройке параметров (забывание, пороги, список критических состояний).

### 2.2. `mchain_quality_report`

**Назначение**  
Предоставляет **детальный анализ качества прогнозов** риска за указанный период для заданного горизонта. Это основной инструмент для оценки точности и калибровки модели.

**Параметры**  
- `p_start` (DATE, по умолч. 7 дней назад) – начало периода.  
- `p_end`   (DATE, по умолч. вчера) – конец периода.  
- `p_horizon` (INT, если NULL – берётся из `markov_config.forecast_horizon_minutes`) – горизонт прогноза в минутах.

**Структура вывода (текстовый отчёт)**  
1. **Общие сведения**: период, количество прогнозов с известным исходом, доля инцидентов, средний предсказанный риск.  
2. **Метрики качества**:  
   - **Brier score** – среднеквадратичная ошибка вероятностей (чем ниже, тем лучше).  
   - **Log-loss** – логистическая потеря (штрафует уверенные неверные прогнозы).  
   - **MAE** – средняя абсолютная ошибка.  
   - **ROC-AUC** – площадь под ROC-кривой (дискриминационная способность, >0.7 хорошо).  
   - **Precision** и **Recall** при пороге 0.5.  
3. **Калибровочная таблица** – разбивка прогнозов на 10 бинов по предсказанной вероятности; для каждого бина: среднее предсказание, наблюдаемая частота инцидентов, количество прогнозов.  
4. **Дневная динамика** метрик (из истории `mchain_quality_metrics_history` или рассчитанная на лету).  
5. **Диагностические сообщения** – причины пропуска расчётов (если недостаточно данных).  
6. **Рекомендации** на основе значений Brier и ROC-AUC.

**Интерпретация ключевых метрик**

| Метрика | Что показывает | Хорошо | Удовлетворительно | Плохо |
|---------|----------------|--------|-------------------|-------|
| **Brier** | Калибровка модели (чем меньше, тем точнее) | < 0.05 | 0.05–0.10 | > 0.20 |
| **ROC-AUC** | Способность различать инциденты и не-инциденты | > 0.70 | 0.60–0.70 | < 0.60 |
| **Log-loss** | Штраф за уверенные ошибки | Чем меньше, тем лучше; сильно зависит от базовой частоты. | | |
| **Precision@0.5** | Доля верных сигналов тревоги (при пороге 0.5) | Высокая (если частота инцидентов не слишком мала) | | |
| **Recall@0.5** | Доля захваченных инцидентов (при пороге 0.5) | Высокая | | |

**Калибровочная таблица** – для идеально откалиброванной модели среднее предсказание в каждом бине должно быть близко к наблюдаемой частоте. Систематическое отклонение (например, завышение в низких бинах) указывает на смещение модели.

**Рекомендации**  
- При плохой калибровке (Brier > 0.2) – проверьте параметры забывания, возможно, модель не успевает адаптироваться к изменениям.  
- При низком ROC-AUC (< 0.6) – пересмотрите определение критических состояний или горизонт прогноза.  
- Если Precision низкая, а Recall высокая – можно повысить порог классификации; если наоборот – снизить порог.

### 2.3. `mchain_summary_report`

**Назначение**  
Предоставляет **сжатый сводный отчёт** по состоянию цепи Маркова, объединяя достоверность прогнозов, анализ переходов в аварию, текущие параметры конфигурации и прогноз риска на заданный горизонт.

**Параметры**  
- `p_start` (TIMESTAMPTZ, по умолч. 7 дней назад) – начало периода для анализа переходов.  
- `p_end`   (TIMESTAMPTZ, по умолч. now()) – конец периода.

**Структура вывода**  
1. **Конфигурация модели**: включено ли адаптивное забывание, параметры alpha, интервал забывания, горизонт прогноза, даты последнего забывания и инцидента.  
2. **Текущее состояние системы**: state_id, параметры (корреляция, тренды), прогноз риска на горизонт из конфигурации (вычисляется через `mchain_predict_risk_current_horizon`).  
3. **Достоверность прогнозов** – полный текст отчёта `mchain_reliability_report`.  
4. **Анализ переходов в аварию** за указанный период – полный текст `mchain_incident_transitions_report` (сравнение сырой статистики и модели с забыванием).  
5. **Итоговые рекомендации** на основе рейтинга достоверности и параметров забывания.

**Интерпретация**  
- **Рейтинг достоверности (0–5)** – интегральная оценка, основанная на объёме данных, стабильности вероятностей и покрытии частых состояний.  
  - 0–2: модель недостаточно обучена, прогнозы ненадёжны.  
  - 3: минимально приемлемо, но требуется осторожность.  
  - 4–5: хорошая и отличная достоверность.  
- **Прогноз риска** – вероятность хотя бы одного попадания в критическое множество в течение указанного горизонта (вычисляется через поглощающую матрицу). Значение > 0.3 обычно сигнализирует о повышенной опасности.  
- **Сравнение долей аварий** – если модель с забыванием показывает существенно более низкую или высокую долю аварий, чем сырая история, это указывает на несоответствие параметров забывания текущей динамике.

**Рекомендации**  
- Используйте для быстрой оценки «здоровья» модели.  
- Если адаптивное забывание отключено – рассмотрите его включение.  
- При давнем отсутствии инцидентов (>14 дней) и включённом адаптивном режиме alpha может опуститься до минимума – при изменении системы выполните ручную коррекцию через `mchain_apply_forgetting(0.05)`.

### 2.4. `mchain_state_transition_matrix_report`

**Назначение**  
Формирует **матрицу переходов между укрупнёнными группами состояний**, чтобы упростить визуализацию и анализ динамики системы. Группировка выполняется по знаку корреляции и трендам (с возможностью включения/исключения тренда ожиданий).

**Параметры**  
- `p_use_weighted` (BOOLEAN, по умолч. TRUE) – взвешивать вероятности по частоте исходных состояний (иначе – простое среднее).  
- `p_include_wait_trend` (BOOLEAN, по умолч. TRUE) – включать ли тренд времени ожидания в группировку (если FALSE – 9 групп: 3×3 для корреляции и OS-тренда; если TRUE – 27 групп: 3×3×3).

**Структура вывода**  
- Таблица, где строки и столбцы – макрогруппы (например, `Neg_down_down`). В ячейках – усреднённая вероятность перехода из группы-строки в группу-столбец.  
- Дополнительно (отключено в текущей версии) выводились переходы из текущего состояния.

**Интерпретация**  
- Матрица позволяет увидеть, между какими макрогруппами происходят наиболее вероятные переходы.  
- Доминирующие диагональные элементы указывают на инерционность системы (состояния сохраняются).  
- Взвешенное усреднение (по умолчанию) даёт более репрезентативную картину, так как учитывает частоту посещения состояний.  
- Группировка по знаку корреляции и трендам помогает выявить, например, склонность системы переходить из негативных состояний в позитивные и наоборот.

**Рекомендации**  
- Используйте для презентаций и дашбордов.  
- При анализе риска обращайте внимание на строки, соответствующие критическим макрогруппам (например, `Neg_down_up`) – высокие вероятности перехода в другие опасные группы могут сигнализировать о каскадных эффектах.

### 2.5. `report_stability_trend`

**Назначение**  
Отслеживает **стабильность вероятностей переходов** во времени. Разбивает заданный период на 7-дневные интервалы и для каждого вычисляет максимальное изменение вероятностей между двумя половинами интервала (`max_prob_change`), а также покрытие и коэффициент стабильности.

**Параметры**  
- `p_lookback_days` (INT, по умолч. 14) – сколько дней назад смотреть (от текущей даты).

**Структура вывода (текстовый отчёт)**  
- Таблица с колонками:  
  - `Период` – 7-дневный интервал.  
  - `max_prob_change` – максимальное изменение вероятностей между первой и второй половиной периода (диапазон 0..1).  
  - `coverage_pct` – доля частых состояний (с частотой >1%), для которых накоплено ≥50 переходов.  
  - `total_transitions` – общее число переходов за период.  
  - `stability_factor` – коэффициент, используемый в адаптивном забывании (1.0, 1.5, 2.0 или 3.0 в зависимости от `max_prob_change`).  
- Интерпретация последнего периода и тренда (улучшение/ухудшение).  
- Рекомендации.

**Интерпретация**  
- **max_prob_change** – чем меньше, тем стабильнее модель.  
  - ≤ 0.05: стабильна.  
  - 0.05–0.2: умеренная нестабильность.  
  - 0.2–0.5: значительная нестабильность.  
  - > 0.5: высокая нестабильность, прогнозы ненадёжны.  
- **coverage_pct** – показывает, достаточно ли данных для надёжной оценки вероятностей. Рекомендуется ≥ 90%.  
- **stability_factor** – используется в `mchain_apply_forgetting` для динамического увеличения alpha при нестабильности, что ускоряет адаптацию.

**Рекомендации**  
- Регулярно проверяйте тренд – если `max_prob_change` растёт, возможно, система меняется быстрее, чем модель успевает адаптироваться.  
- Низкое покрытие (<70%) требует накопления большего объёма данных или пересмотра определения «частых» состояний.

### 2.6. `report_quality_sliding`

**Назначение**  
Возвращает **ежедневные метрики качества прогнозов** за последние `p_window_days` дней, извлекая данные из таблицы `mchain_quality_metrics_history`. Позволяет увидеть динамику Brier, ROC-AUC и количества прогнозов.

**Параметры**  
- `p_window_days` (INT, по умолч. 7) – сколько дней назад смотреть.  
- `p_step_days` (INT, по умолч. 1) – не используется (оставлен для совместимости).

**Структура вывода (таблица)**  
- `period_start` – дата.  
- `total_predictions` – число завершённых прогнозов за день.  
- `brier` – Brier score.  
- `roc_auc` – ROC-AUC.  
- `calibration_notes` – дополнительные замечания (например, «Skipped» если расчёт не производился).

**Интерпретация**  
- Позволяет увидеть, как меняется качество прогнозов день ото дня.  
- Резкие скачки Brier или падения ROC-AUC могут указывать на проблемы с данными, изменение характера системы или сбой в обучении.  
- Если количество прогнозов за день падает ниже порога (обычно 100), метрики могут отсутствовать – это нормально для малоактивных дней.

**Рекомендации**  
- Используйте для оперативного мониторинга – можно настроить алерты при ухудшении Brier или ROC-AUC.  
- Сравнивайте с периодами, когда проводились изменения параметров забывания, чтобы оценить их эффект.

### 2.7. `report_daily_calibration`

**Назначение**  
Выводит **калибровочную кривую** (10 бинов по 0.1) для прогнозов, сделанных в конкретный день. Позволяет детально оценить, насколько предсказанные вероятности соответствуют фактическим частотам инцидентов.

**Параметры**  
- `p_date` (DATE, по умолч. вчера) – день, для которого строится калибровка.

**Структура вывода (массив строк)**  
Каждая строка соответствует одному бину:  
`[bin_low, bin_high): avg_pred=X, obs_freq=Y, cnt=Z`  
где `avg_pred` – среднее предсказание в бине, `obs_freq` – наблюдаемая частота инцидентов, `cnt` – количество прогнозов.

**Интерпретация**  
- Идеальная калибровка: `avg_pred` примерно равен `obs_freq` во всех бинах.  
- Если в низких бинах `obs_freq` выше `avg_pred` – модель недооценивает риск; если ниже – переоценивает.  
- Пустые бины (нет прогнозов) не выводятся.

**Рекомендации**  
- При систематическом смещении в какую-либо сторону можно скорректировать пороги или параметры забывания.  
- Для оценки качества в целом смотрите также Brier score и ROC-AUC.

### 2.8. `state_distribution`

**Назначение**  
Показывает **распределение состояний** системы за последние N дней – сколько раз система оказывалась в каждом состоянии (по целевым состояниям переходов) и какую долю это составляет от общего числа переходов. Дополнительно указывает, является ли состояние критическим.

**Параметры**  
- `p_lookback_days` (INT, по умолч. 7) – период анализа.

**Структура вывода (таблица)**  
- `state_id`, `correlation`, `os_trend`, `wait_trend` – параметры состояния.  
- `transition_count` – количество переходов в это состояние за период.  
- `pct_of_total` – доля от всех переходов (в процентах).  
- `is_critical` – флаг (TRUE/FALSE).

**Интерпретация**  
- Часто посещаемые состояния (высокий `transition_count`) показывают «нормальные» режимы работы системы.  
- Высокая доля критических состояний (`is_critical = TRUE`) может свидетельствовать о нестабильности или неправильном определении критичности.  
- Если какое-то состояние имеет высокую частоту, но не является критическим, это нормально; если критическое состояние часто встречается – это повод для анализа.

**Рекомендации**  
- Используйте для понимания, в каких режимах чаще всего работает система.  
- При изменении состава критических состояний (через `refresh_critical_states`) перепроверьте распределение.

### 2.9. `report_forgetting_effectiveness`

**Назначение**  
Возвращает **результаты экспериментов по подбору параметров забывания** (из таблицы `forgetting_optimization_log`) за последние 14 дней. Позволяет сравнить различные комбинации `base_alpha`, `half_life`, `min_alpha` и `interval_minute` по их влиянию на Brier, ROC-AUC и стабильность.

**Структура вывода (таблица)**  
- `base_alpha`, `half_life`, `min_alpha`, `interval_min` – параметры.  
- `brier` – Brier score на валидационном периоде.  
- `roc_auc` – ROC-AUC.  
- `max_prob_change` – нестабильность (измеренная на обучающем периоде).  
- `total_predictions` – количество прогнозов, использованных для оценки.  
- `is_best` – флаг, указывающий на лучшую комбинацию по Brier.

**Интерпретация**  
- Чем ниже Brier и выше ROC-AUC, тем лучше.  
- Низкое `max_prob_change` говорит о стабильности модели при данных параметрах.  
- Параметры с пометкой `is_best = TRUE` – оптимальные по Brier среди протестированных.

**Рекомендации**  
- Периодически запускайте процедуру `optimize_forgetting_params` для обновления параметров конфигурации.  
- Если текущие параметры сильно отличаются от лучших по Brier, рассмотрите их обновление.  
- Учитывайте, что оптимизация выполняется на исторических данных; при изменении характера системы может потребоваться повторная оптимизация.

---

### 2.10. `mchain_reliability_report`

**Назначение**  
Возвращает **расширенный текстовый отчёт о достоверности прогнозов** на основе трёх метрик: объём данных, стабильность вероятностей и покрытие частых состояний. Результат – интегральный рейтинг от 0 до 5, а также подробная интерпретация и рекомендации.

**Параметры**  
Отсутствуют (использует глобальные данные).

**Структура вывода (текстовый отчёт)**  
1. **Общий рейтинг достоверности (0–5)** с интерпретацией.  
2. **Детализация по метрикам**:  
   - Общее число переходов (`total_transitions`) и порог `min_transitions_for_forgetting`.  
   - Максимальное изменение вероятностей за две недели (`max_prob_change`) и статус стабильности.  
   - Покрытие частых состояний (`coverage_pct`) и статус.  
3. **Рекомендации** в зависимости от рейтинга.

**Интерпретация**  
- Рейтинг 0–2 – модель недостаточно надёжна, прогнозы не рекомендуется использовать.  
- Рейтинг 3 – минимально приемлемо, требуется осторожность.  
- Рейтинг 4–5 – хорошая и отличная достоверность.

**Примечание**  
Данный отчёт используется внутри `mchain_summary_report` и редко вызывается напрямую, но полезен для углублённого анализа.

### 2.11. `mchain_incident_transitions_report`

**Назначение**  
Анализирует **переходы в аварийные состояния** (из таблицы `critical_states`) за указанный временной интервал. Сравнивает сырую статистику из `transition_log` с взвешенными частотами из `markov_frequencies` (модель с учётом забывания).

**Параметры**  
- `p_start` (TIMESTAMPTZ, по умолч. now() - interval '7 days') – начало периода.  
- `p_end`   (TIMESTAMPTZ, по умолч. now()) – конец периода.

**Структура вывода (текстовый отчёт)**  
1. **Сырая статистика (transition_log)**: всего переходов, аварийных переходов, доля, количество различных аварийных состояний.  
2. **Текущая модель (markov_frequencies)**: суммарный вес, вес аварийных переходов, доля.  
3. **Сравнение**: разница долей, объяснение (занижение/завышение риска моделью).  
4. **Динамика по интервалам** (почасово или подневно).  
5. **Рекомендации** на основе доли аварий и расхождений.

**Интерпретация**  
- Если модель с забыванием показывает риск значительно ниже исторического – возможно, alpha слишком высок, и старые аварийные переходы «забыты».  
- Если выше – возможно, alpha слишком низок, и свежие инциденты имеют чрезмерный вес.

**Рекомендации**  
- Используйте для оценки адекватности параметров забывания.  
- Входит в состав `mchain_summary_report`.

### 2.12. `mchain_incident_state_detail_report`

**Назначение**  
Предоставляет **детализированный отчёт по каждому аварийному состоянию** (из `critical_states`), для которого были переходы за указанный период. Для каждого такого состояния выводятся сырая частота, вес в модели с забыванием и топ-3 предшествующих состояния с их частотами.

**Параметры**  
- `p_start` (TIMESTAMPTZ, по умолч. now() - interval '7 days') – начало периода.  
- `p_end`   (TIMESTAMPTZ, по умолч. now()) – конец периода.

**Структура вывода (текстовый отчёт)**  
Для каждого аварийного состояния:  
- state_id, корреляция, тренд ожиданий.  
- Сырых переходов за период.  
- Вес в модели (с забыванием).  
- Топ-3 предшествующих состояния: их state_id, параметры, количество переходов и доля.

**Интерпретация**  
- Позволяет понять, из каких состояний чаще всего происходит попадание в аварию.  
- Высокий вес в модели при низкой сырой частоте может указывать на недавние инциденты, которые ещё не «забыты».

**Рекомендации**  
- Используйте для точечного анализа самых опасных состояний и их причин.  
- Может помочь при ручной корректировке списка критических состояний.

### 2.13. `mchain_health_check`

**Назначение**  
Выполняет **быструю диагностику состояния цепи Маркова** и возвращает статус (`OK`, `WARNING`, `CRITICAL`), краткое сообщение (≤1024 символов) и массив описаний метрик. Предназначен для интеграции с системами мониторинга (например, Zabbix, Prometheus).

**Параметры**  
Отсутствуют.

**Структура вывода (таблица)**  
- `status` – `OK`, `WARNING` или `CRITICAL`.  
- `message` – краткая сводка ключевых метрик (например, `trans=15000, crit=23, risk30=0.12, rel=4`).  
- `description` – массив строк с пояснением значений.

**Проверяемые метрики**  
1. **Достоверность прогнозов** (рейтинг 0–5): если 0 → CRITICAL, <3 → WARNING.  
2. **Рост аварийных переходов** за последние 7 дней по сравнению с предыдущими 7 днями: если >3x → CRITICAL, >2x → WARNING.  
3. **Активность** – отсутствие переходов за последние 10 минут → CRITICAL.  
4. **Наличие данных** в `markov_frequencies` – если пусто → WARNING.  
5. **Забывание** – если прошло более чем в 2 раза больше интервала, чем задано в `interval_minute` → WARNING.

**Интерпретация**  
- `OK` – все показатели в норме.  
- `WARNING` – есть отклонения, требующие внимания, но система работает.  
- `CRITICAL` – требуется срочное вмешательство (модель не обучена, нет данных, резкий рост аварий).

**Рекомендации**  
- Настройте периодический вызов (например, каждые 5–10 минут) и отправку результатов в систему мониторинга.  
- Используйте статус `CRITICAL` для алертов.

## 3. Оптимизация параметров забывания (optimize_forgetting_params)

### 3.1. Общее назначение

Процедура `optimize_forgetting_params` предназначена для автоматического эмпирического подбора параметров адаптивного забывания в цепи Маркова. Она перебирает заданные комбинации параметров, оценивает качество прогнозов на исторических данных для каждой комбинации и выбирает наилучший набор, который затем может быть применён к конфигурации системы (`markov_config`). Это позволяет системе адаптироваться к меняющимся условиям без ручного вмешательства.

---

### 3.2. Сигнатура и параметры

```sql
PROCEDURE optimize_forgetting_params(
    INOUT result TEXT,
    IN p_dry_run BOOLEAN DEFAULT FALSE,
    IN p_force_update BOOLEAN DEFAULT FALSE,
    IN p_verbose BOOLEAN DEFAULT TRUE,
    IN p_min_transitions INT DEFAULT 5,
    IN p_smoothing REAL DEFAULT 0.01,
    IN p_commit_every INT DEFAULT 1
)
```

| Параметр | Тип | По умолчанию | Описание |
|----------|-----|--------------|----------|
| `result` (INOUT) | `TEXT` | – | Возвращает итоговое сообщение о результате оптимизации (обновлена конфигурация или нет, найденные параметры). |
| `p_dry_run` | `BOOLEAN` | `FALSE` | Если `TRUE`, процедура только оценивает параметры и записывает результаты в лог, но **не обновляет** `markov_config`. Полезно для тестирования. |
| `p_force_update` | `BOOLEAN` | `FALSE` | Если `TRUE`, обновляет конфигурацию даже если улучшение Brier меньше порога (0.01). Используется для принудительной смены параметров. |
| `p_verbose` | `BOOLEAN` | `TRUE` | Управляет выводом отладочных сообщений через `RAISE NOTICE`. Отключение (`FALSE`) сокращает объём логов. |
| `p_min_transitions` | `INT` | `5` | Минимальное число переходов для пары состояний, чтобы она учитывалась при расчёте `max_prob_change` (стабильности). Влияет на фильтрацию редких переходов. |
| `p_smoothing` | `REAL` | `0.01` | Параметр аддитивного сглаживания при расчёте вероятностей переходов. Уменьшает влияние редких переходов и предотвращает нулевые вероятности. |
| `p_commit_every` | `INT` | `1` | Частота выполнения `COMMIT` в рамках процедуры (после каждых N итераций). Рекомендуется для быстрого освобождения блокировок и уменьшения размера транзакции. Значение `1` фиксирует транзакцию после каждой комбинации. |

---

### 3.3. Алгоритм работы

#### Шаг 1: Инициализация и настройка

- **Сетка параметров** (жёстко задана внутри процедуры):
  - `base_alpha` – `ARRAY[0.05, 0.10, 0.15, 0.20, 0.25]`
  - `half_life` (дни) – `ARRAY[2, 4, 7, 10, 14]`
  - `min_alpha` – `ARRAY[0.005, 0.010, 0.015, 0.020]`
  - `interval_minute` – `ARRAY[60, 120, 180, 240]`

  Эти массивы при необходимости можно изменить в коде процедуры.

- **Динамическое определение периодов** (на основе фактических данных):
  - **Период обучения** (для построения взвешенных частот) определяется как:
    - Начало: `GREATEST(минимальная дата в transition_log, CURRENT_DATE - 14 дней)` (но не менее 14 дней в прошлом).
    - Конец: `максимальная дата в transition_log` (или `CURRENT_DATE - 1 день`, если данных меньше).
  - **Период оценки** (для вычисления метрик качества) – используется таблица `prediction_log` с известными исходами:
    - Начало: `GREATEST(минимальная дата в prediction_log, начало обучения)`
    - Конец: `максимальная дата в prediction_log` (или `CURRENT_DATE - 1 день`).

- **Проверка достаточности данных:**
  - Если длительность обучения меньше 14 дней → оптимизация отменяется.
  - Если число прогнозов с известным исходом в периоде оценки меньше 50 → оптимизация отменяется.

- **Очистка старого лога:**  
  Удаляются записи из `forgetting_optimization_log` старше 90 дней.

- **Подсчёт общего количества комбинаций:**  
  5 × 5 × 4 × 4 = 400 (при текущих настройках).

#### Шаг 2: Перебор комбинаций параметров

- Выполняются вложенные циклы по каждому параметру.
- Для каждой комбинации вызывается функция `evaluate_forgetting_params` (описана отдельно), которая возвращает:
  - Метрики качества: `brier`, `log_loss`, `roc_auc`, `precision_at_05`, `recall_at_05`, `mae`
  - Метрики стабильности: `max_prob_change`, `coverage_pct`
  - Количество использованных прогнозов: `total_predictions`

- **Фильтрация:**  
  Если `total_predictions < 50`, комбинация пропускается (недостаточно статистики для надёжной оценки).

- **Запись в лог:**  
  Для каждой прошедшей фильтр комбинации вставляется запись в `forgetting_optimization_log` со всеми параметрами и метриками. Изначально все записи имеют `is_best = FALSE`.

#### Шаг 3: Определение лучшей комбинации

- Лучшей считается комбинация с **наименьшим значением Brier score**.
- При обнаружении нового лучшего результата:
  - Обновляется переменная `v_best_brier` и JSON-объект `v_best_params`.
  - Запись в логе помечается `is_best = TRUE`, у предыдущей лучшей сбрасывается флаг.
  - В консоль (если `p_verbose = TRUE`) выводится уведомление.

#### Шаг 4: Отслеживание прогресса

- В начале выводится общее количество комбинаций.
- Каждые 10 комбинаций выводится текущий прогресс в процентах, параметры текущей комбинации и лучший Brier на данный момент.
- По окончании выводится итоговое сообщение с лучшими параметрами и их метриками.

#### Шаг 5: Периодический COMMIT

- После каждой итерации счётчик `v_commit_counter` увеличивается.
- Когда он достигает значения `p_commit_every`, выполняется `COMMIT`, и счётчик сбрасывается.
- Это предотвращает накопление слишком большой транзакции и снижает нагрузку на систему, особенно при большом числе комбинаций.

#### Шаг 6: Обновление конфигурации (если не `p_dry_run`)

- Если найден лучший набор и `p_dry_run = FALSE`:
  - Сравнивается новый Brier с текущим значением `base_alpha` и `half_life` из `markov_config` (используется порог улучшения `0.01`).
  - Если улучшение превышает порог **или** `p_force_update = TRUE`, выполняется `UPDATE markov_config` с новыми значениями.
  - В `result` возвращается сообщение об успешном обновлении или о том, что улучшение незначительно (конфигурация оставлена прежней).
- Если `p_dry_run = TRUE`, конфигурация не изменяется, в `result` возвращается информация о найденных параметрах.

---

### 3.4. Интерпретация результатов

#### 3.4.1. Метрики качества (из `evaluate_forgetting_params`)

- **Brier score** – среднеквадратическая ошибка вероятностного прогноза. Диапазон [0,1], чем меньше, тем лучше. **Основной критерий выбора.**
- **Log‑loss** – логистическая потеря, чувствительна к уверенным неправильным прогнозам.
- **ROC‑AUC** – площадь под ROC-кривой. Характеризует дискриминационную способность. Значение > 0.7 – хорошо, > 0.8 – отлично.
- **Precision и Recall (при пороге 0.5)** – точность и полнота бинарной классификации.
- **MAE** – средняя абсолютная ошибка.

#### 3.4.2. Метрики стабильности и покрытия

- **max_prob_change** – максимальное изменение вероятностей переходов между двумя половинами обучающего периода.  
  - ≤ 0.05 – стабильно  
  - 0.05–0.2 – умеренная нестабильность  
  - 0.2–0.5 – значительная нестабильность  
  - > 0.5 – высокая нестабильность (прогнозы ненадёжны)  
- **coverage_pct** – процент частых состояний (частота > 1%), имеющих не менее 50 переходов в обучающем периоде. ≥ 90% – хорошее покрытие.

#### 3.4.3. Выбор лучших параметров

Лучшая комбинация выбирается **исключительно по минимальному Brier** (при условии ≥ 50 прогнозов). Дополнительно можно учитывать стабильность и покрытие, но в текущей реализации этого нет.

#### 3.4.4. Журнал оптимизации

Таблица `forgetting_optimization_log` содержит все оценённые комбинации, их метрики, флаг `is_best`. Это позволяет:
- Просматривать историю экспериментов.
- Сравнивать метрики для разных параметров.
- Отслеживать, какие параметры были признаны лучшими в каждом запуске.

---

### 3.5. Рекомендации по использованию

#### 3.5.1. Периодичность запуска

Рекомендуется запускать оптимизацию **еженедельно** (например, по воскресеньям в 4:00), чтобы параметры адаптировались к сезонным и трендовым изменениям. При высокой динамике системы частоту можно увеличить до 2 раз в неделю.

#### 3.5.2. Интерпретация прогресса

- `Starting optimization with N combinations` – общее число комбинаций.
- `Progress: X/Y (Z%), current: ...` – текущий номер, процент выполнения, параметры текущей комбинации.
- `New best found at combo ...` – новый лучший Brier достигнут.
- `Optimization finished` – итоговое сообщение с лучшими параметрами и метриками.

#### 3.5.3. Анализ истории

```sql
-- Посмотреть последние запуски и лучшие параметры
SELECT ts, base_alpha, half_life, min_alpha, interval_minute,
       brier, roc_auc, max_prob_change, is_best
FROM forgetting_optimization_log
ORDER BY ts DESC
LIMIT 20;

-- Получить все лучшие параметры за всё время
SELECT * FROM forgetting_optimization_log WHERE is_best = TRUE;
```

#### 3.5.4. Настройка сетки параметров

Измените массивы в коде процедуры, например, добавив промежуточные значения или сузив диапазоны для ускорения. Убедитесь, что значения физически осмысленны.

#### 3.5.5. Использование `p_dry_run`

Перед применением новых параметров в production рекомендуется выполнить сухой запуск, изучить метрики и убедиться, что улучшение действительно ожидается.

#### 3.5.6. Управление транзакциями

Параметр `p_commit_every` позволяет настроить частоту фиксации. Для больших объёмов данных или при возникновении блокировок увеличьте его (например, до 10 или 50), чтобы снизить накладные расходы, но учтите, что при сбое может потеряться часть результатов (они будут зафиксированы только частично). Значение по умолчанию 1 гарантирует минимальный риск потери данных.

---

### 3.6. Возможные ошибки и их решение

| Ошибка / Проблема | Возможная причина | Решение |
|-------------------|-------------------|---------|
| Оптимизация отменена: недостаточно данных обучения (нужно ≥14 дней) | В `transition_log` недостаточно истории | Дождитесь накопления данных или временно используйте ручные параметры. |
| Оптимизация отменена: недостаточно прогнозов для оценки (нужно ≥50) | Мало завершённых прогнозов с известным исходом | Увеличьте период оценки или подождите, пока накопится больше данных. |
| Процесс выполняется слишком долго | Слишком большая сетка параметров или большой объём данных | Сократите количество комбинаций (удалите часть значений из массивов) или уменьшите периоды обучения/оценки. |
| `max_prob_change` всегда = 1.0 | В одной из половин обучающего периода отсутствуют переходы для многих состояний | Увеличьте обучающий период или убедитесь, что система активна в обоих подпериодах. |
| Обновление конфигурации не происходит, хотя найден лучший Brier | Улучшение Brier меньше порога 0.01 | Используйте `p_force_update => TRUE` для принудительного обновления. |
| Блокировки таблиц или длительные транзакции | Одна большая транзакция охватывает все 400 итераций | Установите `p_commit_every` в небольшое значение (например, 1 или 5) для частого COMMIT. |
| Нет записей в `forgetting_optimization_log` | Все комбинации отфильтрованы (меньше 50 прогнозов) | Проверьте период оценки: возможно, прогнозы ещё не завершены. |

## 4. Скрипт-обёртка `optimize_forgetting.sh` и интеграция с cron

### 4.1. Назначение и параметры

Скрипт `optimize_forgetting.sh` выполняет следующие функции:

- Подготавливает SQL-запрос для вызова процедуры `optimize_forgetting_params` с переданными параметрами.
- Запускает этот запрос через `psql`.
- В реальном времени выводит прогресс выполнения в лог-файл (по умолчанию `/tmp/optimize_forgetting_params.log`).
- Обеспечивает корректное логирование и возврат кода ошибки.

Он предназначен для автоматического еженедельного запуска, а также для ручного тестирования.

**Параметры командной строки:**

| Параметр | Тип | По умолчанию | Описание |
|----------|-----|--------------|----------|
| `dry_run` | `true/false` | `false` | Передаётся в процедуру как `p_dry_run`. Если `true`, конфигурация не обновляется. |
| `verbose` | `true/false` | `true` | Передаётся как `p_verbose`. Включает/отключает детальный вывод отладочных сообщений. |
| `commit_every` | целое число | `1` | Передаётся как `p_commit_every`. Определяет частоту выполнения `COMMIT` внутри процедуры. |

**Примеры вызова:**
```bash
# Запуск с обновлением конфигурации (обычный режим)
./optimize_forgetting.sh

# Сухой запуск (только оценка, без обновления)
./optimize_forgetting.sh true

# Сухой запуск с отключением детального вывода и COMMIT каждые 5 итераций
./optimize_forgetting.sh true false 5
```

---

### 4.2. Переменные окружения для подключения к БД

Скрипт использует следующие переменные окружения (с значениями по умолчанию):

```bash
DB_HOST="${DB_HOST:-localhost}"
DB_PORT="${DB_PORT:-5432}"
DB_NAME="${DB_NAME:-expecto_db}"
DB_USER="${DB_USER:-expecto_user}"
```

Пароль должен быть задан либо через переменную `PGPASSWORD`, либо в файле `~/.pgpass`. Это стандартный механизм `psql`.

---

### 4.3. Внутренняя логика скрипта

1. **Проверка наличия `psql`** – если утилита не найдена, скрипт завершается с ошибкой.
2. **Очистка лог-файла** – перед запуском файл `/tmp/optimize_forgetting_params.log` обнуляется.
3. **Создание временного SQL-файла** – в него записывается анонимный блок `DO $$ ... END $$`, который вызывает процедуру с переданными параметрами.
4. **Запуск `tail -f` в фоне** – для вывода прогресса в реальном времени в лог-файл и на экран (через `tee`).
5. **Выполнение SQL-скрипта через `psql`** – вывод добавляется в тот же лог-файл.
6. **Завершение `tail`** – после завершения `psql` фоновый процесс останавливается.
7. **Вывод последних 20 строк лога** – для быстрой проверки результата.
8. **Возврат кода завершения** – соответствует коду, возвращённому `psql`.

Благодаря использованию `tail -f` администратор может наблюдать за прогрессом в реальном времени, даже если запуск выполняется через cron (вывод пишется в лог).

---

### 4.4. Интеграция с cron

В файле `markov_chain_cron.txt` определена следующая строка для еженедельного запуска:

```cron
# Еженедельный подбор параметров забывания (воскресенье в 04:00)
0 4 * * 0 /postgres/pg_expecto/sh/optimize_forgetting.sh false true 1 >> /postgres/pg_expecto/sh/forgetting_optimization.log 2>&1
```

**Разбор:**

- **Время:** каждое воскресенье в 4:00 утра.
- **Команда:** `/postgres/pg_expecto/sh/optimize_forgetting.sh false true 1`
  - `dry_run = false` – обновлять конфигурацию.
  - `verbose = true` – выводить подробные сообщения.
  - `commit_every = 1` – фиксировать транзакцию после каждой итерации (минимальный риск потери данных при сбое).
- **Перенаправление:** весь вывод (stdout и stderr) дописывается в файл `/postgres/pg_expecto/sh/forgetting_optimization.log`. Это обеспечивает сохранение истории всех запусков.

**Зачем запускать в 4:00 воскресенья?**

- Это время минимальной нагрузки на систему (выходной день, ночь).
- Оптимизация может занимать значительное время (перебор до 400 комбинаций) и требует вычислительных ресурсов, поэтому лучше выполнять в часы пик.
- Еженедельный запуск позволяет параметрам адаптироваться к изменениям за прошедшую неделю, но не слишком часто, чтобы избежать излишней «дёрганности».

---

### 4.5. Мониторинг и отладка

- **Лог-файл выполнения:** `/tmp/optimize_forgetting_params.log` – содержит детальный вывод прогресса для последнего запуска (перезаписывается при каждом запуске).
- **Архивный лог:** `/postgres/pg_expecto/sh/forgetting_optimization.log` – хранит историю всех запусков (дописывается).
- **Таблица `forgetting_optimization_log`** – в БД сохраняются метрики для каждой оценённой комбинации параметров. Это позволяет анализировать историю и сравнивать эффективность разных параметров.
- **Статус последнего запуска** – можно проверить через код возврата скрипта (0 – успех, иначе – ошибка).

**Пример просмотра последних результатов в БД:**
```sql
SELECT ts, base_alpha, half_life, min_alpha, interval_minute,
       brier, roc_auc, max_prob_change, is_best
FROM forgetting_optimization_log
ORDER BY ts DESC
LIMIT 10;
```

**Проверка, была ли обновлена конфигурация:**
```sql
SELECT base_alpha, incident_half_life_days, min_alpha, interval_minute
FROM markov_config;
```

---

### 4.6. Рекомендации по эксплуатации

- **Перед первым применением в production** выполните сухой запуск (`dry_run = true`) и проверьте метрики. Убедитесь, что улучшение Brier действительно есть.
- **Если оптимизация выполняется слишком долго** – уменьшите сетку параметров (изменив массивы в коде процедуры) или увеличьте `commit_every` (например, до 10) для сокращения числа COMMIT, но помните, что это увеличит риск потери промежуточных результатов при сбое.
- **Периодически просматривайте лог-файлы** на предмет ошибок (например, недостаток данных, проблемы с подключением к БД).
- **При изменении структуры БД** (например, переименование таблиц) обновите скрипт и процедуру.
- **Для ручного запуска** используйте скрипт с параметрами, например:
  ```bash
  ./optimize_forgetting.sh true true 5   # сухой запуск с COMMIT каждые 5 итераций
  ```

## 5. Управление критическими состояниями

В системе предусмотрены функции для автоматического обновления списка критических состояний на основе эмпирических данных. Это позволяет динамически адаптировать определение «аварийного» состояния к изменяющимся условиям.

### 5.1. `refresh_critical_states`

**Назначение**  
Автоматически обновляет таблицу `critical_states`, используя эмпирические оценки риска, вычисленные функцией `compute_empirical_incident_risk`. Новые состояния добавляются, устаревшие удаляются.

**Параметры**  
- `p_start` (TIMESTAMPTZ, по умолч. now() - interval '14 days') – начало периода анализа.  
- `p_end` (TIMESTAMPTZ, по умолч. now()) – конец периода.  
- `p_min_transitions` (INT, по умолч. 50) – минимальное число переходов для включения состояния.  
- `p_interval_min` (INT, по умолч. 15) – интервал прогноза в минутах для определения инцидента.  
- `p_risk_threshold` (REAL, по умолч. 0.10) – порог эмпирического риска.  
- `p_dry_run` (BOOLEAN, по умолч. FALSE) – если TRUE, только выводит отчёт об изменениях без фактического обновления.  
- `p_audit` (BOOLEAN, по умолч. TRUE) – записывать ли результат в таблицу аудита `critical_states_audit`.

**Возвращаемое значение**  
Текстовый отчёт о количестве добавленных и удалённых состояний.

**Рекомендации**  
- Запускайте еженедельно (например, в воскресенье в 3:00) для поддержания актуальности списка.  
- Используйте `p_dry_run = TRUE` для предварительной оценки изменений.  
- Просматривайте историю в таблице `critical_states_audit` для аудита изменений.

**Пример**  
```sql
SELECT refresh_critical_states(
    p_start => now() - interval '30 days',
    p_risk_threshold => 0.15,
    p_dry_run => TRUE
);
```

---

### 5.2. `compute_empirical_incident_risk`

**Назначение**  
Вычисляет эмпирическую вероятность наступления инцидента в течение заданного интервала времени после каждого перехода в состояние. Использует таблицу `performance_incident` как источник инцидентов.

**Параметры**  
- `p_start` (TIMESTAMPTZ, по умолч. now() - interval '14 days') – начало периода.  
- `p_end` (TIMESTAMPTZ, по умолч. now()) – конец периода.  
- `p_min_transitions` (INT, по умолч. 10) – минимальное число переходов для включения состояния.  
- `p_interval_min` (INT, по умолч. 15) – длина интервала в минутах.

**Возвращаемое значение**  
Таблица с колонками:  
- `state_id`, `correlation`, `os_trend`, `wait_trend` – параметры состояния.  
- `total_transitions` – общее число переходов из этого состояния.  
- `incident_within` – число переходов, после которых в течение интервала начался инцидент.  
- `empirical_risk` – отношение `incident_within / total_transitions`.  
- `lower_bound`, `upper_bound` – 95% доверительный интервал (Уилсон).

**Использование**  
Обычно вызывается внутри `refresh_critical_states`, но может быть полезна и для самостоятельного анализа.

**Пример**  
```sql
SELECT state_id, empirical_risk
FROM compute_empirical_incident_risk(
    p_start => now() - interval '30 days',
    p_interval_min => 15
)
WHERE empirical_risk > 0.15
ORDER BY empirical_risk DESC;
```
