## Подробное описание скрипта `optimize_forgetting.sh`

### 1. Назначение

Скрипт `optimize_forgetting.sh` предназначен для **автоматизированного эмпирического подбора оптимальных параметров адаптивного забывания** в цепи Маркова, используемой для прогнозирования риска инцидентов в системе `expecto_db`.

Адаптивное забывание управляет скоростью «старения» исторических данных: чем выше коэффициент забывания, тем быстрее модель адаптируется к новым условиям, но тем меньше она помнит прошлые паттерны. Неправильный выбор параметров может привести к недообучению или переобучению. Скрипт перебирает сотни комбинаций четырёх ключевых параметров, оценивает их качество по объективным метрикам (Brier score, ROC‑AUC, log‑loss и др.) и, при необходимости, обновляет конфигурацию модели наилучшими значениями.

---

### 2. Логика работы скрипта

#### 2.1. Внешний интерфейс

Скрипт написан на Bash и служит обёрткой над хранимой процедурой PostgreSQL `optimize_forgetting_params`. Он выполняет следующие шаги:

1. **Проверяет наличие клиента `psql`** в системе.
2. **Парсит переданные аргументы** (см. раздел «Параметры»).
3. **Формирует временный SQL-файл**, содержащий вызов процедуры с переданными параметрами.
4. **Запускает `psql`** с этим файлом, перенаправляя весь вывод в лог-файл `/tmp/optimize_forgetting_params.log`.
5. **В фоне запускает `tail -f`** для вывода лога в реальном времени на терминал, чтобы пользователь видел прогресс.
6. **По завершении** останавливает `tail`, выводит последние 20 строк лога и возвращает код возврата `psql`.

#### 2.2. Внутренняя логика процедуры `optimize_forgetting_params` (выполняется на стороне БД)

Процедура реализована на PL/pgSQL и выполняет следующие действия:

- **Динамическое определение периодов**:
  - **Обучающий период** (`learn_start` – `learn_end`) – берётся из минимальной и максимальной дат в таблице `transition_log` (или по умолчанию последние 14 дней). Этот период используется для построения взвешенных частот переходов с экспоненциальным старением (параметр `half_life`).
  - **Валидационный период** (`eval_start` – `eval_end`) – определяется по наличию завершённых прогнозов с известными исходами в таблице `prediction_log`. На этих данных вычисляются метрики качества для каждой комбинации параметров.

- **Перебор комбинаций параметров по сетке**:
  - `base_alpha` — базовый коэффициент забывания (массив `[0.05, 0.1, 0.15, 0.2, 0.25]`).
  - `half_life` — период полураспада веса инцидентов (дни; массив `[2, 4, 7, 10, 14]`).
  - `min_alpha` — минимальный коэффициент забывания (массив `[0.005, 0.01, 0.015, 0.02]`).
  - `interval_minute` — интервал между применениями забывания (минуты; массив `[60, 120, 180, 240]`).

  Общее число комбинаций: 5×5×4×4 = 400.

- **Для каждой комбинации** вызывается вспомогательная функция `evaluate_forgetting_params`, которая:
  - Строит временную матрицу переходов с учётом экспоненциального взвешивания (`weight = exp(-(learn_end - ts) / half_life)`).
  - Применяет аддитивное сглаживание (параметр `p_smoothing = 0.01`) для предотвращения нулевых вероятностей.
  - Для всех прогнозов из валидационного периода вычисляет риск с использованием этой матрицы (функция `mchain_predict_risk_k_v2_with_matrix`).
  - Рассчитывает метрики качества: `brier`, `log_loss`, `roc_auc`, `precision_at_05`, `recall_at_05`, `mae`, а также `max_prob_change` (стабильность) и `coverage_pct` (покрытие частых состояний).
  - Если число прогнозов меньше 50, комбинация пропускается.

- **Логирование каждой комбинации** в таблицу `forgetting_optimization_log` с пометкой `is_best` для наилучшего набора по Brier score.

- **Выбор лучшей комбинации** (по минимальному Brier) и, если не включён режим `dry_run`, **обновление конфигурации** (`markov_config`) новыми параметрами.

- **Периодический COMMIT** (через каждые `commit_every` итераций) для освобождения блокировок и снижения нагрузки на транзакционный лог.

- **Возврат итогового сообщения** через выходной параметр `result`, который затем выводится в лог скрипта.

### 3. Параметры скрипта (командная строка)

| Параметр       | Тип      | По умолчанию | Описание                                                                                                                                 |
|----------------|----------|--------------|------------------------------------------------------------------------------------------------------------------------------------------|
| `dry_run`      | `true`/`false` | `false` | Если `true`, процедура выполняет полный расчёт, выбирает лучшие параметры, **но не обновляет** `markov_config`. Полезно для тестирования. |
| `verbose`      | `true`/`false` | `true`  | Включает детальный вывод прогресса в лог (каждая 10-я комбинация, уведомления о новом лучшем результате).                                |
| `commit_every` | число          | `1`     | Частота выполнения `COMMIT` внутри процедуры (каждые N комбинаций). Увеличение значения ускоряет выполнение, но может увеличить риск потери прогресса при сбое. |

Примеры вызова:

```bash
# Сухой запуск с выводом прогресса (без обновления конфига)
./optimize_forgetting.sh true true 1

# Полноценный запуск с коммитом каждые 5 итераций
./optimize_forgetting.sh false true 5
```

### 4. Настройка подключения к базе данных

Скрипт использует переменные окружения для подключения к PostgreSQL:

| Переменная   | Назначение                | Значение по умолчанию |
|--------------|---------------------------|-----------------------|
| `DB_HOST`    | Адрес сервера БД          | `localhost`           |
| `DB_PORT`    | Порт                      | `5432`                |
| `DB_NAME`    | Имя базы данных           | `expecto_db`          |
| `DB_USER`    | Имя пользователя          | `expecto_user`        |

Пароль можно задать через переменную окружения `PGPASSWORD` или использовать файл `.pgpass` в домашней директории.

Пример задания переменных перед запуском:

```bash
export PGPASSWORD=mysecret
export DB_HOST=192.168.1.100
./optimize_forgetting.sh false true 1
```

### 5. Логирование и мониторинг

- **Основной лог-файл**: `/tmp/optimize_forgetting_params.log`  
  Содержит полный вывод `psql` – сообщения `RAISE NOTICE` из процедуры, а также все строки, выводимые в терминал.

- **Во время выполнения** скрипт показывает прогресс в реальном времени (благодаря `tail -f`), что позволяет отслеживать:
  - номер текущей комбинации и общее количество;
  - текущие проверяемые параметры;
  - улучшение лучшего Brier score;
  - завершение перебора и итоговые рекомендации.

- **После завершения** в лог записывается код возврата и последние 20 строк, что упрощает диагностику.

---

### 6. Когда и как часто запускать

Оптимизацию рекомендуется проводить **не чаще одного раза в неделю**, например, по воскресеньям (это уже заложено в `markov_chain_cron.txt` – строка `0 4 * * 0`).  
Причины:

- Для достоверной оценки необходимо накопить достаточное число прогнозов с известными исходами (не менее 50, но лучше >100).
- Процесс перебора 400 комбинаций может занимать от нескольких минут до часа в зависимости от объёма данных и производительности сервера.
- Частая оптимизация даёт незначительный прирост качества и создаёт лишнюю нагрузку.

---

### 7. Что делать с результатами

- После успешного выполнения (не dry-run) параметры в `markov_config` обновляются автоматически.
- Все протестированные комбинации сохраняются в таблице `forgetting_optimization_log` – можно проанализировать их вручную:

```sql
SELECT * FROM forgetting_optimization_log 
ORDER BY brier ASC NULLS LAST LIMIT 10;
```

- Если по каким-то причинам качество ухудшилось, можно вручную восстановить предыдущие параметры из истории или запустить скрипт с `dry_run = true`, чтобы увидеть, какие параметры были бы выбраны, и принять решение.

---

### 8. Особенности реализации

- **Аддитивное сглаживание** (`p_smoothing = 0.01`) предотвращает появление нулевых вероятностей, что критично для вычисления log‑loss.
- **Динамическое определение периода** – процедура автоматически подстраивается под доступные исторические данные, что делает её устойчивой к изменениям в наполнении БД.
- **Периодический COMMIT** снижает риск долгих транзакций и помогает избежать конфликтов блокировок в производственной среде.
- **Обработка ошибок** – если данных недостаточно (менее 14 дней обучения или менее 50 прогнозов для валидации), процедура завершается с информативным сообщением, а скрипт возвращает код 0 (без обновлений).

---

### 9. Заключение

`optimize_forgetting.sh` – это готовый к использованию инструмент для автоматической настройки адаптивного забывания цепи Маркова. Он позволяет поддерживать модель в актуальном состоянии без ручного вмешательства, повышая качество прогнозов риска. Благодаря гибким параметрам, логгированию и режиму dry-run, скрипт безопасен для запуска как в тестовой, так и в боевой среде. Регулярное использование (еженедельно) обеспечивает стабильную работу системы прогнозирования при изменяющихся паттернах нагрузки.
