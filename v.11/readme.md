# Цепь Маркова для прогнозирования аварийных ситуаций

[![PostgreSQL](https://img.shields.io/badge/PostgreSQL-15+-316192?logo=postgresql&logoColor=white)](https://www.postgresql.org/)
[![Версия](https://img.shields.io/badge/версия-11.8-blue)](https://github.com/your-repo/markov-chain)
[![Лицензия](https://img.shields.io/badge/лицензия-Apache%202.0-blue)](https://www.apache.org/licenses/LICENSE-2.0)

Данный модуль реализует **цепь Маркова** для прогнозирования риска возникновения инцидентов производительности в СУБД PostgreSQL на основе текущих метрик операционной скорости и времени ожидания. Система непрерывно обучается на потоке данных, использует **адаптивное забывание** для учёта изменений в поведении системы и предоставляет **прогнозы риска** с настраиваемым горизонтом, а также широкий набор отчётов для мониторинга и анализа качества модели.

---

## Общее описание механизма

Модель основана на **дискретных состояниях**, каждое из которых определяется тремя параметрами:

- **Коэффициент корреляции** (`correlation`) – значение от –1.0 до +1.0 с шагом 0.1 (21 градация);
- **Тренд операционной скорости** (`os_trend`) – одно из трёх значений: –1 (снижение), 0 (стабильно), +1 (рост);
- **Тренд времени ожидания** (`wait_trend`) – аналогично: –1, 0, +1.

Всего получается **189 состояний** (21 × 3 × 3). Они хранятся в справочнике `state_descriptions`.

Каждую минуту система получает текущие значения метрик (через внешнюю функцию `get_current_os_waiting_correlation_for_markov_chain`), определяет идентификатор состояния и логирует переход между предыдущим и текущим состояниями. На основе накопленных частот переходов строятся **вероятности переходов**, которые используются для прогнозирования риска попадания в **критические (аварийные) состояния**.

Критические состояния **не заданы жёстко**, а динамически обновляются на основе эмпирических данных об инцидентах (таблица `performance_incident`). Это позволяет модели адаптироваться к изменяющимся условиям работы системы.

---

## Корневая функция `mchain_train_step()`

Является **основным шагом обучения** и должна вызываться **каждую минуту** (например, через cron или pgAgent). Её алгоритм:

1. **Получение текущих метрик** – вызывает внешнюю функцию, возвращающую корреляцию, тренд OS и тренд wait. Если метрики недоступны, функция завершается.
2. **Инициализация справочника** – при первом вызове заполняется таблица `state_descriptions` (через `fill_state_descriptions()`).
3. **Определение текущего состояния** – через `get_state_id()` преобразует метрики в числовой идентификатор (0…188).
4. **Чтение предыдущего состояния** – из таблицы `markov_chain` (хранит только одну строку с предыдущим и текущим состоянием).
5. **Логирование перехода** – вызывает `mchain_log_transition()`, которая:
   - вставляет запись в `transition_log` (история всех переходов);
   - обновляет накопленные частоты в `markov_frequencies`.
6. **Обновление текущего состояния** – записывает новые метрики в `markov_chain`.
7. **Плановое забывание** – если с момента последнего забывания прошло больше заданного интервала (`interval_minute`), вызывается `mchain_apply_forgetting()`.
8. **Формирование прогноза** – вызывает `collect_prediction()`, которая создаёт запись в `prediction_log` с прогнозом риска на горизонт, указанный в конфигурации (`forecast_horizon_minutes`).

Таким образом, каждая минута система обновляет модель и генерирует новый прогноз.

## Обучение цепи Маркова

### Накопление частот

Все переходы сохраняются в таблице `transition_log` (с временной меткой) и агрегируются в таблице `markov_frequencies` в виде **весов** (необязательно целых). При каждом переходе частота для пары `(from_state, to_state)` увеличивается на 1.0.

### Пересчёт вероятностей

Функция `update_markov_probabilities()` пересчитывает условные вероятности по формуле:

```
P(to_state | from_state) = frequency / SUM(frequency) OVER (PARTITION BY from_state)
```

Результат сохраняется в таблице `markov_probabilities`, которая используется для прогнозирования.

## Адаптивное забывание

Забывание необходимо, чтобы модель не «застревала» в прошлых паттернах и быстро реагировала на изменение поведения системы. Параметры забывания хранятся в таблице `markov_config`:

- `adaptive_forgetting_enabled` – глобальное включение/выключение (по умолчанию `TRUE`);
- `use_adaptive_alpha` – если `TRUE`, коэффициент забывания вычисляется динамически;
- `base_alpha` – базовый коэффициент (при частых инцидентах);
- `min_alpha` – минимальный коэффициент (при очень редких инцидентах);
- `incident_half_life_days` – период полураспада влияния последнего инцидента;
- `interval_minute` – периодичность применения забывания (в минутах);
- `min_transitions_for_forgetting` – минимальное число переходов, после которого забывание разрешено.

При вызове `mchain_apply_forgetting()`:

1. Проверяется достаточность данных (`mchain_check_sufficiency()`), которая возвращает флаг `sufficient` и коэффициент нестабильности `stability_factor`.
2. Если данных недостаточно, забывание пропускается.
3. Если `use_adaptive_alpha = TRUE`, эффективный alpha вычисляется по формуле:

   ```
   effective_alpha = base_alpha * exp(-days_since_incident / half_life)
   ```

   где `days_since_incident` – число дней с момента последнего аварийного перехода (обновляется триггером). Значение ограничивается `min_alpha` и дополнительно умножается на `stability_factor` (чтобы усилить забывание при нестабильных вероятностях).
4. Все частоты в `markov_frequencies` умножаются на `(1 - effective_alpha)`, а затем удаляются записи с частотами менее `1e-6`.
5. Пересчитываются вероятности (`update_markov_probabilities`), обновляется время последнего забывания.

## Прогнозирование риска

### Алгоритм

Для прогноза риска **не используется поглощающая матрица**. Вместо этого применяется **итеративное обнуление вероятностей** критических состояний (функция `mchain_predict_risk_k_v2`):

1. Задаётся начальный вектор распределения вероятностей: 1.0 в текущем состоянии (если оно не критическое).
2. На каждом шаге (минуте) вектор умножается на матрицу `markov_probabilities`, получая распределение через 1 минуту.
3. Вероятности, попавшие в критические состояния (`critical_states`), добавляются к накопленному риску, а затем **обнуляются** в векторе (чтобы не учитывать повторные попадания).
4. Процесс повторяется `k` раз, где `k` – горизонт прогноза в минутах (берётся из `markov_config.forecast_horizon_minutes`).
5. Возвращается суммарная вероятность хотя бы одного попадания в критическое множество за `k` шагов.

Этот подход даёт более точную оценку риска, чем использование поглощающей матрицы, и легко адаптируется к динамическому списку критических состояний.

### Горизонт прогноза

Горизонт задаётся в таблице `markov_config` полем `forecast_horizon_minutes` (по умолчанию 30 минут). Он используется во всех прогнозах (`collect_prediction`, `update_prediction_outcomes`, отчётах). Это обеспечивает единообразие и упрощает настройку.

## Динамические критические состояния

В версии 11 отказались от жёсткого условия `correlation<0 AND os_trend=-1 AND wait_trend=1` в пользу **динамического списка** `critical_states`. Этот список обновляется автоматически на основе эмпирических данных об инцидентах.

### Функция `compute_empirical_incident_risk`

Для каждого состояния (из `state_descriptions`) вычисляется:

- `total_transitions` – число переходов **из** этого состояния за анализируемый период;
- `incident_within` – число переходов, после которых в течение заданного интервала (по умолчанию 15 минут) начался инцидент (из таблицы `performance_incident`);
- `empirical_risk` = `incident_within / total_transitions`.

Также рассчитываются границы 95% доверительного интервала (Уилсон).

### Функция `refresh_critical_states`

Вызывается по расписанию (например, еженедельно) и:

1. Вычисляет эмпирические риски для всех состояний за последние 14 дней (настраивается).
2. Сравнивает полученный список с текущим содержимым `critical_states`.
3. Добавляет новые состояния с риском выше порога (по умолчанию 0.10) и минимальным числом переходов (по умолчанию 50).
4. Удаляет состояния, которые перестали удовлетворять критериям.
5. Логирует изменения в таблицу `critical_states_audit`.

Таким образом, модель автоматически адаптируется к изменению профиля инцидентов.

## Оценка достоверности прогнозов

### Рейтинг достоверности (`mchain_forecast_reliability`)

Возвращает целое число от 0 до 5 на основе трёх компонентов:

- **Объём данных** (число переходов): менее 100 → 0, 100–500 → 1, 500–5000 → 2, более 5000 → 3.
- **Стабильность вероятностей** (`max_prob_change`): максимальное изменение вероятностей переходов за последние 14 дней. Чем меньше изменение, тем выше бонус.
- **Покрытие частых состояний**: доля состояний с частотой >1%, для которых накоплено ≥50 переходов. Если покрытие ≥90% и нестабильность низкая, добавляется бонус.

Итоговый рейтинг используется в отчётах и для принятия решений о надёжности прогнозов.

### Метрики качества

Для прогнозов, сохранённых в `prediction_log`, вычисляются:

- **Brier score** – среднеквадратичная ошибка вероятности;
- **Log-loss** – логистическая потеря;
- **ROC‑AUC** – площадь под ROC-кривой;
- **Precision / Recall** при пороге 0.5;
- **MAE** – средняя абсолютная ошибка;
- **Калибровочная кривая** – разбивка по 10 бинам вероятностей.

Ежедневно (по расписанию) вызывается `calculate_daily_quality_metrics`, которая агрегирует эти метрики и сохраняет в таблицу `mchain_quality_metrics_history`.

## Основные отчёты

Модуль предоставляет богатый набор отчётов (все возвращают текст или таблицы):

- `mchain_summary_report` – сводный отчёт о состоянии модели, включая достоверность, переходы в критические состояния и текущий прогноз.
- `mchain_quality_report` – подробный отчёт о качестве прогнозов за указанный период (метрики, калибровка, динамика).
- `mchain_incident_transitions_report` – анализ переходов в критические состояния (исторические и по модели с забыванием).
- `mchain_incident_state_detail_report` – детализация по каждому критическому состоянию.
- `mchain_state_transition_matrix_report` – матрица переходов между макрогруппами состояний (9 или 27 групп).
- `report_stability_trend` – мониторинг стабильности вероятностей по 7‑дневным периодам.
- `report_quality_sliding` – скользящее качество прогнозов по дням.
- `report_daily_calibration` – калибровочная кривая за конкретный день.
- `state_distribution` – распределение состояний и частота критических.
- `report_forgetting_effectiveness` – эффективность забывания (результаты оптимизации).
- `generate_full_analytical_report` – **сводный аналитический отчёт** в формате Markdown, включающий все перечисленные разделы.

## Cron-задачи (расписание)

Для автоматического обслуживания модели используются следующие задания cron:

| Время | Команда | Назначение |
|-------|---------|------------|
| `15 1 * * *` | `SELECT mchain_clean_transition_log();` | Очистка журнала переходов старше заданного срока (по умолчанию 14 дней). |
| `0 2 * * *` | `SELECT mchain_clean_apply_forgetting_log();` | Очистка журнала забывания. |
| `0 2 * * *` | `SELECT calculate_daily_quality_metrics(CURRENT_DATE - 1, 30);` | Расчёт суточных метрик качества (за вчерашний день, горизонт 30 мин). |
| `*/5 * * * *` | `SELECT update_prediction_outcomes();` | Обновление исходов для прогнозов, у которых истёк горизонт. |
| `0 3 * * 0` | `SELECT refresh_critical_states();` | Еженедельное обновление списка критических состояний (воскресенье, 03:00). |
| `0 4 * * 0` | `/postgres/pg_expecto/sh/optimize_forgetting.sh false true 1` | Еженедельный эмпирический подбор параметров забывания (воскресенье, 04:00). |

## Эмпирический подбор параметров адаптивного забывания

Для автоматической настройки параметров забывания (`base_alpha`, `half_life`, `min_alpha`, `interval_minute`) реализована процедура `optimize_forgetting_params()`.

### Принцип работы

1. Определяются периоды обучения (последние 14 дней переходов) и валидации (прогнозы с известными исходами).
2. Задаётся сетка значений для каждого параметра (по умолчанию: alpha ∈ [0.05, 0.1, 0.15, 0.2, 0.25], half_life ∈ [2, 4, 7, 10, 14], min_alpha ∈ [0.005, 0.01, 0.015, 0.02], interval ∈ [60, 120, 180, 240]).
3. Для каждой комбинации:
   - строится взвешенная матрица частот с экспоненциальным затуханием (используя заданные `base_alpha` и `half_life`);
   - вычисляются прогнозы для всех записей в валидационном периоде с использованием этой матрицы;
   - рассчитываются метрики качества (Brier, log-loss, ROC‑AUC и др.);
   - результат сохраняется в таблицу `forgetting_optimization_log`.
4. Выбирается комбинация с наименьшим Brier score.
5. Если не включён режим `dry_run`, обновляются параметры в `markov_config`.

Процедура выполняется еженедельно по cron, что позволяет модели автоматически подстраиваться под долгосрочные изменения.

## Заключение

Реализация цепи Маркова версии 11.8 представляет собой **полностью автоматизированную систему прогнозирования риска**, которая:

- обучается в реальном времени на потоке метрик;
- адаптивно забывает устаревшие данные;
- динамически определяет критические состояния на основе фактических инцидентов;
- предоставляет прогнозы с настраиваемым горизонтом;
- оценивает собственное качество и достоверность;
- содержит широкий набор отчётов для мониторинга и анализа;
- самостоятельно подбирает оптимальные параметры забывания.

Это делает её пригодной для использования в production-средах, где поведение системы постоянно меняется, а требования к точности прогнозов высоки.
