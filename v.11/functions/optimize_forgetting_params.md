## Подробное описание алгоритма работы и интерпретации результатов функции `optimize_forgetting_params`

### 1. Общее назначение

Функция `optimize_forgetting_params` предназначена для автоматического эмпирического подбора параметров адаптивного забывания в цепи Маркова. Она перебирает заданные комбинации параметров, оценивает качество прогнозов на исторических данных для каждой комбинации и выбирает наилучший набор, который затем может быть применён к конфигурации системы (`markov_config`). Это позволяет системе адаптироваться к меняющимся условиям без ручного вмешательства.

---

### 2. Входные параметры

| Параметр | Тип | По умолчанию | Описание |
|----------|-----|--------------|----------|
| `p_dry_run` | `BOOLEAN` | `FALSE` | Если `TRUE`, функция только оценивает параметры и записывает результаты в лог, но **не обновляет** `markov_config`. Полезно для тестирования. |
| `p_force_update` | `BOOLEAN` | `FALSE` | Если `TRUE`, обновляет конфигурацию даже если улучшение Brier меньше порога (0.01). Используется при необходимости принудительной смены параметров. |
| `p_verbose` | `BOOLEAN` | `TRUE` | Управляет выводом отладочных сообщений через `RAISE NOTICE`. Отключение (`FALSE`) сокращает объём логов. |

---

### 3. Алгоритм работы (пошагово)

#### Шаг 1: Инициализация и настройка
- **Определение сетки параметров:**  
  В начале функции задаются массивы возможных значений для:
  - `base_alpha` (базовый коэффициент забывания) – значения: 0.05, 0.10, 0.15, 0.20, 0.25
  - `half_life` (период полураспада в днях) – 2, 4, 7, 10, 14
  - `min_alpha` (минимальный коэффициент забывания) – 0.005, 0.010, 0.015, 0.020
  - `interval_minute` (интервал применения забывания в минутах) – 60, 120, 180, 240

  Эти массивы легко редактируются для изменения диапазона поиска.

- **Периоды анализа:**  
  - Обучение (для построения взвешенных частот): последние 60 дней (`CURRENT_DATE - 60` … `CURRENT_DATE - 1`).
  - Оценка (для вычисления метрик качества): последние 30 дней (`CURRENT_DATE - 30` … `CURRENT_DATE - 1`).  
  При необходимости периоды можно изменить в коде.

- **Очистка старого лога:**  
  Удаляются записи в `forgetting_optimization_log` старше 90 дней, чтобы таблица не разрасталась.

- **Подсчёт общего количества комбинаций:**  
  Вычисляется произведение длин массивов, используется для индикации прогресса.

#### Шаг 2: Перебор комбинаций параметров
Функция выполняет вложенные циклы по каждому параметру. Общее количество комбинаций = 5 × 5 × 4 × 4 = 400 (при текущих настройках). Для каждой комбинации:

- **Вызов `evaluate_forgetting_params`:**  
  Передаются текущие параметры и периоды. Функция возвращает:
  - Метрики качества: `brier`, `log_loss`, `roc_auc`, `precision_at_05`, `recall_at_05`, `mae`
  - Метрики стабильности: `max_prob_change`, `coverage_pct`
  - Количество использованных прогнозов: `total_predictions`

- **Фильтрация:**  
  Если количество прогнозов с известным исходом в периоде оценки меньше 50, такая комбинация пропускается (недостаточно статистики).

#### Шаг 3: Запись результатов в лог
Для каждой комбинации, прошедшей фильтр, вставляется запись в таблицу `forgetting_optimization_log` со всеми параметрами и полученными метриками. Записи помечаются как `is_best = FALSE` (изначально).

#### Шаг 4: Определение лучшей комбинации
Лучшей считается комбинация с **наименьшим значением Brier score** (чем меньше, тем лучше калибровка). При обнаружении нового лучшего результата:
- Обновляется переменная `v_best_brier` и `v_best_params`.
- Для соответствующей записи в логе устанавливается `is_best = TRUE`, а для всех остальных – сбрасывается.
- В консоль выводится уведомление (если `p_verbose = TRUE`) о новом лучшем результате.

#### Шаг 5: Вывод прогресса выполнения
Для отслеживания хода выполнения функция выводит:
- Стартовое сообщение с общим числом комбинаций.
- Каждые 10 комбинаций – текущий прогресс в процентах, текущие параметры и лучший Brier на данный момент.
- При обнаружении нового лучшего результата – соответствующее уведомление.
- По окончании – итоговое сообщение с лучшими параметрами и их метриками.

#### Шаг 6: Обновление конфигурации (если не `p_dry_run`)
Если найден лучший набор параметров и `p_dry_run = FALSE`:
- Проверяется, превышает ли улучшение Brier порог `v_improvement_threshold` (0.01) по сравнению с текущей конфигурацией (если `p_force_update = FALSE`).
- Если улучшение значимо (или `p_force_update = TRUE`), выполняется `UPDATE markov_config` с новыми значениями.
- Возвращается текстовое сообщение с подтверждением обновления или с информацией о том, что улучшение незначительно (конфигурация не изменена).

Если `p_dry_run = TRUE`, конфигурация не обновляется, а только возвращается сообщение о найденных лучших параметрах.

### 4. Интерпретация результатов

#### 4.1. Метрики качества
- **Brier score** – среднеквадратическая ошибка вероятностного прогноза. Диапазон [0,1], чем меньше, тем лучше. Является основной целевой метрикой для выбора лучших параметров.
- **Log‑loss** – логистическая потеря, чувствительна к уверенным неправильным прогнозам. Может быть очень высокой при плохой калибровке.
- **ROC‑AUC** – площадь под ROC-кривой. Оценивает дискриминационную способность (способность разделять инциденты и не-инциденты). Значение > 0.7 считается хорошим, > 0.8 – отличным.
- **Precision и Recall (при пороге 0.5)** – показывают точность и полноту при бинарной классификации. Используются для оценки практической полезности прогнозов.
- **MAE** – средняя абсолютная ошибка, простая интерпретация (в единицах вероятности).

#### 4.2. Метрики стабильности и покрытия
- **max_prob_change** – максимальное изменение вероятностей переходов между двумя половинами обучающего периода. Характеризует **стабильность** матрицы переходов. Чем меньше, тем стабильнее модель. Значение > 0.2 указывает на сильную нестабильность, что снижает доверие к прогнозам, даже если калибровка хороша.
- **coverage_pct** – процент частых состояний (частота > 1%), имеющих не менее 50 переходов в обучающем периоде. Отражает **представительность** данных. Значение ≥ 90% – хорошее покрытие.

#### 4.3. Критерий выбора лучших параметров
Лучшей считается комбинация с **наименьшим Brier score**, при условии, что количество прогнозов в оценке ≥ 50. Дополнительно можно учитывать стабильность и покрытие, но в текущей реализации выбор основан исключительно на Brier.

#### 4.4. Логирование и мониторинг
Все результаты сохраняются в таблицу `forgetting_optimization_log`. Это позволяет:
- Просматривать историю экспериментов.
- Сравнивать разные комбинации параметров.
- Анализировать, как меняется качество при изменении параметров.
- Отслеживать, когда и какие параметры были признаны лучшими.

Записи с `is_best = TRUE` показывают, какие параметры были выбраны в каждом запуске (если обновление происходило).

### 5. Рекомендации по использованию

#### 5.1. Периодичность запуска
Рекомендуется запускать оптимизацию **еженедельно** (например, по воскресеньям в 4:00), чтобы параметры адаптировались к сезонным и трендовым изменениям. При высокой динамике системы частоту можно увеличить до двух раз в неделю.

#### 5.2. Интерпретация вывода прогресса
- `Starting optimization with N combinations` – общее количество комбинаций для перебора.
- `Progress: X/Y (Z%), current: ...` – показывает текущий номер комбинации, общее количество, процент выполнения и параметры текущей комбинации. Это позволяет оценить время завершения.
- `New best found at combo ...` – указывает, что для текущей комбинации достигнут наилучший Brier.
- `Optimization finished` – итоговое сообщение с лучшими параметрами и метриками.

#### 5.3. Анализ истории экспериментов
Используйте SQL-запросы для:
- Поиска лучших параметров за всё время: `SELECT * FROM forgetting_optimization_log WHERE is_best = TRUE;`
- Построения графиков зависимости метрик от параметров (с помощью внешних инструментов).
- Оценки стабильности выбора параметров (если лучшие параметры сильно меняются от запуска к запуску, это может указывать на нестабильность процесса).

#### 5.4. Настройка сетки параметров
При необходимости измените массивы в коде функции:
- Для более мелкого поиска добавьте промежуточные значения (например, `0.075`, `0.125`).
- Для ускорения можно сократить количество вариантов.
- Убедитесь, что диапазоны физически осмысленны (например, `half_life` не должен быть меньше 1 дня).

#### 5.5. Использование `p_dry_run`
Перед первым применением рекомендуется выполнить сухой запуск и изучить полученные метрики. Это позволит убедиться, что функция работает корректно и улучшение Brier действительно ожидается.

### 6. Возможные ошибки и их решение

| Ошибка / Проблема | Возможная причина | Решение |
|-------------------|-------------------|---------|
| `round(real, integer)` не существует | Округление значения типа `real` без приведения к `numeric` | Убедитесь, что в коде используется `round(value::numeric, 4)` (исправлено в текущей версии). |
| Отсутствуют прогнозы в периоде оценки (`total_predictions = 0`) | В указанном периоде нет завершённых прогнозов (например, только начали сбор данных) | Увеличьте период оценки или дождитесь накопления данных. |
| Процесс выполняется слишком долго | Слишком большая сетка параметров или большой объём данных | Уменьшите количество комбинаций или сократите периоды обучения/оценки. |
| `max_prob_change` всегда = 1.0 | В одной из половин обучающего периода отсутствуют переходы для многих состояний | Увеличьте обучающий период или проверьте, что система активна в обоих подпериодах. |
| Обновление конфигурации не происходит, хотя найден лучший Brier | Улучшение Brier меньше порога (`v_improvement_threshold`) | Используйте `p_force_update => TRUE` для принудительного обновления. |

---

### 7. Примеры использования

#### Базовый запуск с обновлением конфигурации
```sql
SELECT optimize_forgetting_params();
```

#### Сухой запуск для тестирования
```sql
SELECT optimize_forgetting_params(p_dry_run => TRUE);
```

#### Запуск с принудительным обновлением и отключением детального вывода
```sql
SELECT optimize_forgetting_params(p_force_update => TRUE, p_verbose => FALSE);
```

#### Просмотр последних результатов
```sql
SELECT ts, base_alpha, half_life, min_alpha, interval_minute,
       brier, roc_auc, max_prob_change, is_best
FROM forgetting_optimization_log
ORDER BY ts DESC
LIMIT 10;
```

### Заключение

Функция `optimize_forgetting_params` представляет собой полностью автоматизированный механизм для подбора параметров адаптивного забывания на основе исторических данных. Её использование позволяет системе самостоятельно адаптироваться к изменениям, минимизируя ручное вмешательство. Регулярный запуск, мониторинг метрик и анализ логов обеспечат поддержание высокого качества прогнозов в долгосрочной перспективе.
